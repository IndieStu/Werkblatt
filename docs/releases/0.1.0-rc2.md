# Werkblatt 0.1.0rc2

Tag: `v0.1.0-rc.2`

Status: Release Candidate

## Zweck und Freigabegrenze

Dieser Release Candidate aktualisiert den kontrollierten Single-Tenant-
Pilotbetrieb bei Zircula e.V. Er ist kein allgemeiner Hosted-Multi-Tenant-
Release. Vor Aufnahme einer zweiten Organisation in dieselbe Instanz bleibt
der dokumentierte Multi-Tenant-Ausbau ein hartes Gate.

## Enthaltene Änderungen

- Kalender ist die Standardansicht der Workshopübersicht;
- jeder User kann persönlich dauerhaft zwischen Kalender und Liste wechseln;
- manuell erfasste Teilnehmende können als spontan oder außerhalb von Pretix
  angemeldet gekennzeichnet werden;
- die Teilnehmerherkunft wird in Statistik und Revisionssnapshot berücksichtigt;
- echte Pretix-Einträge bleiben gegen manuelle Herkunftsänderungen und
  Entfernung geschützt.

## Update von 0.1.0rc1

1. exakten Release-Tag beziehungsweise Image-Digest festhalten;
2. Datenbank und private Medien gemeinsam sichern;
3. `python manage.py migrate --check` mit dem neuen Image ausführen;
4. `python manage.py migrate --noinput` separat vom Webstart ausführen;
5. ausschließlich den Webcontainer ersetzen;
6. interne Readiness, öffentlichen Healthcheck, Login und Logs prüfen;
7. Kalender-/Listenpräferenz und die manuelle Teilnehmerherkunft mit
   synthetischen Daten prüfen;
8. regulären Pretix-Abgleich kontrolliert ausführen.

Die additive Migration `identities.0004_user_preferred_workshop_view` setzt
für bestehende und neue User den Kalender als persönliche Standardansicht.
Sie verändert keine Workshops, Dokumentationen oder Teilnehmerdaten.

## Rollback

Vorheriges Image, dessen Digest und der Pre-Update-Datenstand müssen bis zur
Abnahme erhalten bleiben. Die neue Spalte ist additiv und wird von rc1
ignoriert. Bei einem reinen Anwendungsfehler kann daher nach fachlicher
Prüfung das vorherige Image verwendet werden. Falls eine Datenrücksetzung
erforderlich ist, werden Datenbank und private Medien nur gemeinsam aus
demselben Backupstand wiederhergestellt.

## Releaseartefakte

Vor Veröffentlichung beziehungsweise Tagging werden dokumentiert:

- Git-Commit und signierter Tag oder nachvollziehbar erstellter Tag;
- OCI-Image-ID beziehungsweise Digest und commitgenaue Source-URL;
- Python- und Container-CycloneDX-SBOM;
- `pip-licenses`-Metadatenreport;
- `THIRD_PARTY_LICENSES.md` samt Lock-Baseline;
- vollständiger CI-Status und produktiver Smoke-Test.
